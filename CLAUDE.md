# Part 1: Project Overview

**Cosmos Strategic Capability Platform** scales a premium, facilitator-led strategy consulting methodology into a self-serve, interactive SaaS product ("DIY Consulting"). Instead of grading users against compliance checklists, it confronts executive teams with **restlessness-arousing questions** — e.g. *"If every customer left, who would be the last to leave and why?"* — and drives **Guided Self-Evaluation**: the user compares their own answer against AI-generated benchmark answers at three depths (Level 1 superficial → Level 3 insight-driven) instead of being graded by an external consultant.

**Core business problems this addresses** (full detail: [BRD](documentation/product/brd.md)):
- Traditional strategic training has high churn and no evidence it changes real-world outcomes.
- Treating senior professionals as "students" creates stature asymmetry and low engagement — the platform treats users as peers.
- Classic stage-gate templates optimize for compliance/form-filling, not deep thinking.

**POC Scope**: the **Insights Module** — SWOT, Opportunity, and Consumer Analysis through the Insight Spiral — validating the hypothesis that an LLM-backed RAG engine can support Guided Self-Evaluation without a live human facilitator.

**Engagement Delivery Mode** (added 2026-09-05): every project has a `delivery_mode` — `consultant_guided_async` (the default, and the only one with real behavior behind it), `diy_self_serve`, or `live_online`. The field is real and editable (Consultant-only, via the project setup page's dropdown), but only `consultant_guided_async` does anything different today — the other two are captured now, undesigned, so project setup doesn't need a second schema/UI change once they're built. See [Roadmap](documentation/product/roadmap.md)'s "Engagement Delivery Modes" section for the three-way split and a cited architectural precedent for the live mode.

**Cosmos-Owned Content Repositories** (added 2026-09-05): two related requirements, sub-project (a) now built, sub-project (b) still not. (1) **Cosmos Knowledge Uploads — done 2026-09-06**: the shared Framework Knowledge Base (`framework_kb_chunks`), previously seeded only from two bundled startup PDFs, now has a SystemAdmin-only upload path (`POST/GET/DELETE /api/admin/framework-knowledge[/{id}]`, pdf/docx/pptx/txt/md/xlsx, synchronous ingestion reusing `project_knowledge_base.py`'s extractors, tracked in a new `framework_kb_sources` table). **AI Framework Generation was also built on top of it** — `backend/framework_db.py`'s `generate_framework_from_knowledge(rag, project)` retrieves broadly from the widened Framework Knowledge Base and prompts the active LLM provider to draft a full stage/question set, replacing a project's template-cloned framework wholesale and flagging every drafted question `ai_generated=true`. Two entry points: automatic (`POST /api/projects` with `delivery_mode="diy_self_serve"`) and manual (`POST /api/projects/{id}/framework/generate`, Consultant-only, any delivery mode — the retry path). The function never raises and leaves the framework untouched on any failure. Frontend: an admin "Framework Knowledge" tab, a delivery-mode dropdown at project creation, a "Generate Framework from Cosmos Knowledge" button, and an "AI-drafted" badge. (2) **Cosmos Case Study Repository — still not built, still undesigned**: a reusable, Cosmos-owned library of case studies a Consultant selects from at project setup, instead of uploading a fresh external case study per engagement, formalizing what Balaji asked Ashutosh for on the 2 Sept call. See [Roadmap](documentation/product/roadmap.md)'s "Cosmos-Owned Content Repositories" section.

**User roles** (full detail: [Functional Spec](documentation/product/functional-spec.md)): `SystemAdmin` (global — creates projects), `Consultant` (per-project — preps the engagement, uploads artifacts, activates it), `ClientUser` (per-project — works the learning flow). Revised 2026-08-24 from an earlier four-role Admin/Owner/Reviewer/Peer draft — see Part 5.

**Guided Learning Flow** (added 2026-08-24, from a stakeholder review meeting — full detail: [Functional Spec §2.3](documentation/product/functional-spec.md)): baseline concept calibration against the org's own definitions, adaptive question difficulty, keyword-agnostic answer mapping, a two-case-study resolution flow (external + internal, with a hidden reveal), user-driven self-evaluation with a corpus-relative depth signal, and a module-end Start/Stop/Continue reflection. **Two of these are done**: adaptive question difficulty (probe-then-escalate, landed 2026-08-26) and baseline concept calibration (`backend/calibration_db.py`, a `calibration_awaiting_answer` chat phase, and a Consultant-authored "Baseline Calibration" editor — landed 2026-09-01, see `docs/superpowers/specs/2026-09-01-baseline-calibration-design.md`). The rest — keyword-agnostic mapping, case study resolution, the corpus-relative depth signal, Start/Stop/Continue — are not built yet. **A 2026-09-02 stakeholder call raised open questions that may reshape this flow before further work proceeds** — chiefly whether baseline calibration should stay pre-question (as built) or move post-question/become a two-point before-and-after design, and whether consultant-uploaded documents (the Engagement Knowledge Base this flow depends on) stay in scope as currently built. See [Stakeholder Clarifications](documentation/product/stakeholder-clarifications-2026-09.md), pending a 2026-09-09 planning session — nothing has changed in the code as a result yet.

# Part 2: Architecture

Three-tier: Presentation (Next.js/React, TypeScript) → Application API (FastAPI) → storage. **Storage is now one Neon Postgres database with `pgvector`** for the Framework Knowledge Base — decided and built 2026-08-24 (Phase 0) — see [Neon Postgres + pgvector Spec](docs/superpowers/specs/2026-08-24-neon-postgres-pgvector-design.md). The Engagement Knowledge Base's `pgvector` tables (`project_kb_chunks`, etc.) are still target-only, not yet built. Full detail, diagrams, and the proposed longer-term "Framework Factory" architecture: [Architecture Overview](documentation/architecture/overview.md).

**Core data flow (single, live flow as of 2026-08-31 — the old `/api/evaluate` split described in earlier versions of this file no longer applies; that endpoint and its hardcoded cases were retired, not just left in place)**:

`POST /api/chat/sessions` (body `{project_id}`) starts a continuous chat interview, backed by `backend/chat_engine.py` — this is what `frontend-react/`'s chat page actually calls:
1. User answers a strategic question inline in the chat.
2. For each question, `RagEngine.search_merged` runs a `pgvector` cosine-distance query merged across the shared Framework Knowledge Base (`framework_kb_chunks`) AND the project's own Engagement Knowledge Base (`project_kb_chunks`), source-tagged — **implemented**.
3. The active LLM provider (Anthropic direct API by default, switchable to OpenAI/Gemini via `platform_settings`) generates Level 1/2/3 comparative benchmark answers (`RagEngine.generate_comparative_benchmarks`) — **implemented**; the frontend renders these as a split-screen comparison with source references.
4. User self-evaluates (notes + a Needs Work/Satisfactory/Strong status), saved via `POST /api/projects/{id}/responses` — upsertable per `(question_id, project_id)` via `COALESCE` so separate save calls don't clobber each other — **implemented**.
5. `GET /api/projects/{id}/brief` compiles all of a project's saved responses into a markdown strategic brief, grouped by stage, in `sequence_order` — downloadable from the chat UI — **implemented**.

A standalone, non-chat `POST /api/projects/{id}/evaluate` also exists (same retrieval/benchmark pipeline, no persistence) — built during Backend API Integration but never wired into any frontend page; the chat flow above generates benchmarks internally instead. `chat_engine.py` also still supports a legacy `case_id` mode (`backend/cases_data.py`, the old Blazar/Basil case studies) as an internal alternative to `project_id` — nothing actively deleted it, but there is no REST endpoint or frontend UI left to reach it. Every session the frontend creates today is `project_id`-based.

**Graceful degradation**: no active LLM provider credentials configured → local heuristic critique fallback. No/unparseable archive PDFs → synthetic in-memory vector dataset. This means the app (and its tests) run fully offline.

**Real Users & Auth landed 2026-08-28 (Phase A)** — `users` table, `POST /api/auth/register`/`login`, `GET /api/auth/me`, `get_current_user` dependency (`backend/auth.py`, `backend/users_db.py`). **Real Projects landed 2026-08-28 (Phase B)** — `projects`/`project_members` tables, `backend/projects_db.py`, `require_admin`/`require_project_role`/`require_active_project` dependencies, and `/api/projects` (create/list/detail/update/activate). **A per-project Engagement Knowledge Base landed 2026-08-28 (Phase C)** — `project_artifacts`/`project_kb_chunks` tables, `backend/project_artifacts_db.py`, `backend/project_knowledge_base.py` (document/audio parsing, chunking, embedding, synchronous ingestion), and `/api/projects/{id}/artifacts` (upload/list/delete) — a Consultant uploads a customer's own documents/audio for one engagement, isolated from every other project via `project_id`-scoped `pgvector` chunks. **A project-scoped comparative-benchmark evaluation flow landed 2026-08-28 (Backend API Integration)** — `RagEngine.search_merged` (blends the Framework KB above with a project's Engagement KB, source-tagged), `RagEngine.generate_comparative_benchmarks` (Level 1/2/3 benchmarks), `backend/responses_db.py`, `backend/brief.py`, and `/api/projects/{id}/evaluate`/`/responses`/`/brief`. **Frontend GUI Overhaul landed 2026-08-31** — `frontend-react/` was fully wired to this and the rest of the `/api/projects/*`/`/api/auth/*` surface (login/register, project dashboards, project setup, client hub, the chat interview flow described above), and the legacy `/api/evaluate`, `CASES_DATA`, `GET /api/cases`, `GET /api/case/{case_id}`, and the frontend's `mockProjectState.ts` mock were **retired**, not left in place. **Admin UI and project-member management also landed 2026-08-31** — an `/admin` page (Users tab, Projects tab) and `POST/GET/PATCH/DELETE /api/projects/{id}/members[/{user_id}]`, closing the "no way to add a ClientUser" gap. Full design: [Users/Projects/Engagement KB Spec](docs/superpowers/specs/2026-08-24-users-projects-engagement-kb-design.md), architecture detail: [Architecture Overview §3](documentation/architecture/overview.md).

**An async artifact-ingestion pipeline landed 2026-09-02 — built in code, not deployed** (there is still no live GCP deployment for anything in this repo, same status as the rest of the Cloud Run plan in Part 6). Artifact upload is now dual-mode on whether `GCS_ARTIFACTS_BUCKET` is set (same convention as the existing `GCS_TRANSCRIBE_BUCKET`): **set** (deployed envs) → `POST /api/projects/{id}/artifacts` streams the bytes to `gs://cosmos-artifacts-{env}/raw/{project_id}/{artifact_id}/{filename}` (`backend/gcs_artifact_storage.py`), marks the row `Queued`, and returns immediately; an Eventarc object-finalized trigger then invokes **a second deployable FastAPI service** — `backend/processor_main.py`, Cloud Run `cosmos-artifact-processor` — which runs the *same* `ingest_artifact` core, moves the object to `processed/`/`failed/`, and records the final status plus `gcs_object_path`. **Unset** (local dev, CI, the pytest suite) → ingestion runs inline in the upload request exactly as before, nothing is persisted to GCS, `gcs_object_path` stays `null`, and the offline guarantee is unchanged. Eventarc's GCS-direct triggers can only match on bucket/type — there is no object-name-prefix filter — so the processor's own writes to `processed/`/`failed/` re-invoke it; it returns `200 skipped` for any non-`raw/` payload rather than 500ing into a days-long retry stream. The GCP resources are provisioned by the repo's first Terraform module, `infra/terraform/artifact-pipeline/`. Full design: [Async Artifact Ingestion Pipeline Spec](docs/superpowers/specs/2026-09-02-artifact-ingestion-pipeline-design.md).

# Part 3: Tech Stack & Directory Structure

**Backend (current)**: Python 3.10+, FastAPI, Neon Postgres + `pgvector` (`psycopg2-binary`, `DATABASE_URL` env var) for both the relational tables and the Framework Knowledge Base vector index, `SentenceTransformer("all-MiniLM-L6-v2")` for local embeddings, a pluggable LLM provider layer (`backend/llm_providers/`) supporting Anthropic (default, direct API), OpenAI, and Gemini (via Vertex AI), switchable at runtime by a SystemAdmin through `platform_settings` and a stopgap shared-token admin gate (`ADMIN_API_TOKEN`) — a real `require_admin` dependency now exists (Phase B) but hasn't been wired into `/api/admin/settings` to replace it; that's a separate, not-yet-made decision. Real Users & Auth (Phase A, 2026-08-28): `passlib[bcrypt]` for password hashing, `python-jose[cryptography]` for JWT issuance/verification (`HS256`, 24h expiry, `JWT_SECRET_KEY` env var, no hardcoded fallback) — `backend/auth.py`, `backend/users_db.py`. Note: `passlib` 1.7.4 requires `bcrypt<4.1` pinned in `requirements.txt` (its version probe breaks on newer bcrypt). Real Projects (Phase B, 2026-08-28): `backend/projects_db.py` (project CRUD + membership), `require_admin`/`require_project_role`/`require_active_project` dependencies in `backend/auth.py`. Real Engagement Knowledge Base (Phase C, 2026-08-28): `backend/project_artifacts_db.py`, `backend/project_knowledge_base.py` — `python-docx`/`python-pptx` (document parsing, alongside the already-present `pypdf`), `google-cloud-speech`/`google-cloud-storage` (Google Speech-to-Text audio transcription, migrated 2026-09-01 from the original AWS Transcribe/`boto3` implementation to align with the GCP platform decision below; gracefully degrades to a `'Transcript Needed'` artifact status when `GCS_TRANSCRIBE_BUCKET` isn't set, the audio format isn't one of the supported encodings (mp3/wav/flac/ogg — m4a isn't supported by Speech-to-Text and always falls back), or GCP is otherwise unavailable, mirroring the codebase's existing graceful-degradation philosophy), the same `SentenceTransformer` embedding model `rag_engine.py` already loads (passed in, not duplicated). Async artifact ingestion (2026-09-02): `openpyxl` for `.xlsx` extraction (batched-row chunking) and `.md` reusing the existing plain-text extractor — supported formats are now pdf/docx/pptx/txt/md/xlsx/audio; `google-cloud-storage` again for `backend/gcs_artifact_storage.py`'s raw→processed/failed object moves; and **Terraform** (`hashicorp/google`, `infra/terraform/artifact-pipeline/`) — the repo's first infrastructure-as-code. `backend/processor_main.py` deliberately constructs a bare `SentenceTransformer("all-MiniLM-L6-v2")` (wrapped to the `.embedding_model` shape `ingest_artifact` expects) rather than a full `RagEngine`, whose `__init__` also runs `load_or_build_index()` and would let a processor cold start write into the *shared* Framework KB. Ingestion is still synchronous and inline on the upload request when `GCS_ARTIFACTS_BUCKET` is unset; when it's set, the work moves to the Eventarc-invoked processor service — no background job queue either way. Backend API Integration (2026-08-28): `backend/process_db.py`, `backend/responses_db.py`, `backend/brief.py`, and two new `RagEngine` methods (`search_merged`, `generate_comparative_benchmarks`) — no new third-party dependencies, reuses the existing embedding model and LLM provider plumbing. `LLMProvider.complete()` accepts a multi-turn message history, not just a single prompt, supporting the chat-style interview flow (`backend/chat_engine.py`). Consultant-Initiated Client Invites (2026-09-09): a new `password_setup_tokens` table, `backend/invite_tokens_db.py`, and `requests` (added to send transactional email via the Resend API in `backend/email_provider.py`, gracefully degrading to a returned setup link when `RESEND_API_KEY` isn't set). SQLite and the flat-file vector JSON were retired in Phase 0 (2026-08-24).
**Frontend**: Next.js (React, TypeScript), in `frontend-react/` — migrated from the earlier vanilla HTML/CSS/JS frontend on 2026-08-27. Calls the FastAPI backend over HTTP via `NEXT_PUBLIC_API_BASE`.
**Testing**: `pytest` + FastAPI `TestClient` (`httpx`) — a test bed exists (`tests/`, 379 tests, run via `pytest` from the repo root) covering the LLM Provider Abstraction modules, the chat-style interview modules (`chat_sessions`, `chat_engine`, `chat_endpoints`), the Phase A auth modules (`users_db`, `auth`, `/api/auth/*` endpoints), the Phase B project modules (`projects_db`, the new `auth` dependencies, `/api/projects/*` endpoints), the Phase C Engagement KB modules (`project_artifacts_db`, `project_knowledge_base`, `/api/projects/*/artifacts*` endpoints), the Backend API Integration modules (`process_db`, `responses_db`, `brief`, `RagEngine.search_merged`/`generate_comparative_benchmarks`, the new `/api/projects/*/evaluate`/`/responses`/`/brief` endpoints), the Framework Authoring Mode modules (`framework_db`, the `/api/projects/*/framework/*` endpoints), and the Baseline Calibration modules (`calibration_db`, the `/api/projects/*/framework/calibration*` endpoints, `chat_engine`'s calibration phase), and the async ingestion pipeline modules (`gcs_artifact_storage`, `processor_main`, the `.md`/`.xlsx` extractors, the dual-mode upload/delete endpoint paths); the broader pre-migration API contract suite is still planned, not yet built (see Part 5). A GitHub Actions CI workflow (`.github/workflows/ci.yml`) runs the full suite on every push/PR to `main`.

# Part 4: Data & API

**This section describes the current, live schema and API — there is no separate "pre-migration" API left.** `documentation/development/technical-spec.md` describes an earlier target design and has not been fully reconciled with what's below in every last section; where they conflict, this file and the actual code (`backend/main.py`) win.

**`responses` table**: `project_id`-based (`self_evaluation_notes`/`self_evaluation_status`, not the old SQLite shape's `rating`/`critique`/`recommendations`), added as DDL in Phase B and read/written starting with Backend API Integration (`backend/responses_db.py`).

**`project_artifacts` table**: `status` is `Uploaded` (the DDL default) → `Queued` (added 2026-09-02, set once the file is staged in GCS) → `Processing` → `Indexed` / `Transcript Needed` / `Failed`; `source_format` is `pdf`/`docx`/`pptx`/`txt`/`md`/`xlsx`/`audio` (`md`/`xlsx` added 2026-09-02); nullable `gcs_object_path` (also 2026-09-02) holds the object's current location and stays `null` in local/CI mode. Both CHECK constraints and the new column are widened by an idempotent migration in `database.init_db`.

**Current API** (`backend/main.py`) — grouped by area, not declaration order:

| Endpoint | Behavior today |
|---|---|
| `GET /api/status` | Vector DB size, active LLM provider. |
| `POST /api/auth/register` | Body `{email, password, full_name}` → creates a `users` row (bcrypt-hashed password), returns `{id, email, full_name, is_active, is_admin, created_at}`; `400` on duplicate email. |
| `POST /api/auth/login` | Body `{email, password}` → `{access_token, token_type: "bearer"}` (JWT, `HS256`, 24h expiry); `401` with the same message for unknown email or wrong password (no account-existence leak). |
| `GET /api/auth/me` | Requires `Authorization: Bearer <token>`; returns the caller's user dict via the `get_current_user` dependency; `401` on a missing/invalid/expired token or a deleted user. |
| `POST /api/auth/accept-invite` | Public (Consultant-Initiated Client Invites, landed 2026-09-09). Body `{token, password}` → sets the pending account's password and logs it in, returning `{access_token, token_type: "bearer"}`; `404` for an unknown token or if the account it names no longer exists; `400` if the token is already consumed or expired. |
| `GET /api/admin/users`, `POST /api/admin/users`, `PATCH /api/admin/users/{id}`, `POST /api/admin/users/{id}/reset-password` | **SystemAdmin-only** (`require_admin`). List/create/update (`full_name`/`is_admin`/`is_active`)/reset-password for any user; an admin cannot demote or deactivate themself (`400`). Backs the Admin UI's Users tab. |
| `POST /api/admin/framework-knowledge` | **SystemAdmin-only** (`require_admin`, Cosmos Knowledge Uploads, landed 2026-09-06). Multipart `file`; infers format from the filename (pdf/docx/pptx/txt/md/xlsx — no audio); synchronously extracts/chunks/embeds it into the shared `framework_kb_chunks` table (reusing `project_knowledge_base.py`'s extractors) and records a `framework_kb_sources` row. `400` on an unsupported extension; `413` over 50MB. |
| `GET /api/admin/framework-knowledge` | **SystemAdmin-only**. Lists all `framework_kb_sources` rows (filename/format/uploader/status). |
| `DELETE /api/admin/framework-knowledge/{source_id}` | **SystemAdmin-only**. Deletes a source and its `framework_kb_chunks` rows (FK cascade); `404` if unknown. |
| `POST /api/projects` | **SystemAdmin-only**. Body `{name, customer_name, description?, industry_context?, consultant_user_id}` → clones the template process into a fresh `"{name} Framework"` process (Framework Authoring Mode), creates a `Draft` project pointed at the clone, and its initial `Consultant` `project_members` row, atomically; `403` if not admin; `400` on an invalid `consultant_user_id`. |
| `GET /api/projects` | Any authenticated user; lists every project where the caller has a `project_members` row. Each project object includes the caller's own `role` (`Consultant`/`ClientUser`) on that project (added 2026-09-01 so the frontend can route/filter by role instead of showing every member the Consultant UI). |
| `GET /api/projects/{id}` | Requires a `project_members` row for that project (`Consultant` or `ClientUser`); a `ClientUser` additionally gets `403` while the project is `Draft` (a `Consultant` may view their own `Draft` project). Response includes the caller's own `role` on this project, same as above. |
| `PATCH /api/projects/{id}` | **Consultant-only** (of that project). Partial update of `name`/`customer_name`/`description`/`industry_context`/`delivery_mode`; `400` if `delivery_mode` isn't one of `consultant_guided_async`/`diy_self_serve`/`live_online`; `403` if not that project's Consultant; `404` if the project doesn't exist. |
| `POST /api/projects/{id}/activate` | **Consultant-only** (of that project); `Draft` → `Active`; `403` if not Consultant; `400` if the project isn't currently `Draft`. |
| `POST/GET/PATCH/DELETE /api/projects/{id}/members[/{user_id}]` | `POST` is Consultant-only (looks the invitee up by email, `404` if unregistered); `GET`/`PATCH` (role)/`DELETE` are Consultant-**or**-Admin (`require_admin_or_consultant`); `PATCH` role must be `Consultant` or `ClientUser`. Landed 2026-08-31 — closes the "no way to add a ClientUser" gap. |
| `POST /api/projects/{id}/invite-client` | **Consultant-only** (of that project, Consultant-Initiated Client Invites, landed 2026-09-09). Body `{email, full_name}`. If the email already belongs to a registered user: adds them to the project only if not already a member, and — if that account is still pending (`password_hash IS NULL`) — always issues a fresh one-time setup token/link/email regardless of prior membership, so a lost or already-used link can be reissued. If the email is new: creates a pending account, adds it to the project, and issues the token/link/email. Emails via `backend/email_provider.py` (Resend); `email_sent: false`/`setup_link` returned for the Consultant to copy when `RESEND_API_KEY` isn't set or an already-activated existing user is added. `400` on blank fields or an invalid FK. |
| `POST /api/projects/{id}/artifacts` | **Consultant-only** (of that project). Multipart `file` + optional `purpose` (default `reference`); infers format from the filename (pdf/docx/pptx/txt/md/xlsx/audio). **Dual-mode since 2026-09-02** — with `GCS_ARTIFACTS_BUCKET` set it streams the bytes to `raw/{project_id}/{artifact_id}/{filename}` in a threadpool, flips the row to `Queued`, and returns immediately (the Eventarc-invoked processor finishes the job); unset, it runs ingestion inline in a threadpool (parse/transcribe → chunk → embed → insert — moved off the event loop 2026-08-30 after a large upload froze the whole backend) and returns the artifact's post-ingestion state. `403` if not Consultant; `400` on an unsupported extension or invalid FK; `413` over 50MB. |
| `GET /api/projects/{id}/artifacts` | Any project member (`Consultant` or `ClientUser`); lists that project's artifacts (incl. status/purpose/transcript_text); `403` if not a member. |
| `DELETE /api/projects/{id}/artifacts/{artifact_id}` | **Consultant-only** (of that project); deletes the artifact — its `project_kb_chunks` rows cascade automatically via FK, and since 2026-09-02 the GCS object at the row's current `gcs_object_path` (`raw/`, `processed/` or `failed/`) is deleted first when one exists. A `NotFound` from GCS is treated as success (nothing to delete — an already-gone object must never make a row undeletable); any other GCS failure is a `500` and the row is left in place. `403` if not Consultant; `404` if the artifact doesn't exist or belongs to a different project. |
| `GET /api/process/{process_id}` | Any authenticated user; full process detail nested stages → questions → guidance, ordered; `404` if unknown. |
| `GET /api/projects/{id}/framework`, `POST/PATCH/DELETE .../framework/stages[/{id}]`, `POST/PATCH/DELETE .../framework/stages/{id}/questions` or `.../framework/questions/{id}` | **Consultant-only** (Framework Authoring Mode, landed 2026-09-01). Each project owns a cloned copy of the framework process (see `POST /api/projects` above); these seven endpoints add/rename/reorder/delete stages and questions, and upsert per-question guidance. Blank `name`/`text`/`level`/`owner_role`/`reviewer_role` values are rejected (`400`). |
| `GET/POST /api/projects/{id}/framework/calibration`, `PATCH/DELETE .../framework/calibration/{concept_id}` | **Consultant-only** (Baseline Calibration, part of Guided Learning Flow, landed 2026-09-01). A Consultant-authored list of core concepts (name + this org's own definition) that a fresh chat session runs through — informational only, never blocking — before the project's first real question. See `docs/superpowers/specs/2026-09-01-baseline-calibration-design.md`. |
| `POST /api/projects/{project_id}/framework/generate` | **Consultant-only** (AI Framework Generation, landed 2026-09-06). Drafts a full stage/question set from the Framework Knowledge Base via the active LLM provider and replaces the project's current stages/questions wholesale, flagging each drafted question `ai_generated=true`; also triggered automatically at `POST /api/projects` when `delivery_mode="diy_self_serve"`. Returns `{generated: boolean, framework}` — `generated: false` means the LLM draft failed and the existing framework was left untouched (deleting old stages/questions **cascades to `responses`** via `ON DELETE CASCADE`, so a successful regeneration also deletes any client answers/self-evaluations already saved against the replaced questions). |
| `POST /api/projects/{id}/evaluate` | Any project member of an `Active` project. Body `{question_id, submitted_text}` → `{question_id, level_1, level_2, level_3, source_chunks}` — merged Framework + Engagement KB retrieval (`RagEngine.search_merged`), Level 1/2/3 comparative benchmarks (`RagEngine.generate_comparative_benchmarks`, falls back to fixed local content if the LLM errors or returns an incomplete response); `400` if `question_id` doesn't belong to the project's `process_id`; `404` if unknown. Does **not** persist. Built during Backend API Integration but **not called by the current frontend** — the chat flow below generates benchmarks internally instead of hitting this endpoint. |
| `POST /api/projects/{id}/responses` | Any project member of an `Active` project. Body `{question_id, submitted_text?, self_evaluation_notes?, self_evaluation_status?}` → the saved response row. Upsertable per `(question_id, project_id)` via `COALESCE` — a call that omits a field preserves its previously-saved value rather than nulling it out. Same cross-process `400`/`404` validation as `/evaluate`. |
| `GET /api/projects/{id}/brief` | Any project member of an `Active` project. Returns `{project_id, markdown}` — a compiled markdown summary of all the project's saved responses (`backend/brief.py`), grouped by stage, in `sequence_order`. |
| `GET /api/projects/{id}/stage-progress` | Gated identically to `/evaluate`/`/responses`/`/brief` (`require_project_member` then `require_active_project`). Returns `{"stages": [{"id", "name", "sequence_order", "question_count"}, ...]}` (`backend/process_db.get_stage_summary`) — stage names and per-stage question counts only, never question text or Consultant guidance. Landed 2026-09-10 with the Chat Interview Screen UI/UX Redesign (Part 5), backing the chat page's persistent stage-progress sidebar; a running sum of `question_count` lines up with `chat_sessions.current_level_index` since both are ordered by `sequence_order`. |
| `POST /api/chat/sessions` | Body `{project_id}` (the live path — every session the frontend creates is project-scoped) or the legacy `{case_id}` (still accepted by `chat_engine.py`, but no REST/UI path reaches it since `GET /api/cases` was retired); exactly one of the two is required. Starts a continuous chat interview; returns the session and its first question. |
| `POST /api/chat/sessions/{id}/messages` | Advances the interview's phase state machine with the user's reply — internally calls `RagEngine.search_merged`/`generate_comparative_benchmarks` for `project_id` sessions and persists self-evaluations via `responses_db`; returns newly generated assistant message(s). |
| `GET /api/chat/sessions/{id}` | Full message history + current phase/level, for resuming a session. |
| `GET /api/admin/settings`, `PATCH /api/admin/settings` | Read/switch the active LLM provider (`anthropic`/`openai`/`gemini`). Gated by a stopgap shared-token check (`ADMIN_API_TOKEN`), not `require_admin` — see Part 5. |
| `GET /api/admin/projects`, `PATCH /api/admin/projects/{id}`, `PATCH /api/admin/projects/{id}/status`, `DELETE /api/admin/projects/{id}` | **SystemAdmin-only**. List every project (not just the caller's), edit any project's fields, force its `status` to `Draft`/`Active` (bypassing the normal Consultant-only activate flow), or delete it. Backs the Admin UI's Projects tab. Landed 2026-08-31. |

**Removed, not just superseded** (2026-08-31, once the above was fully wired into `frontend-react/`): `CASES_DATA`, `GET /api/cases`, `GET /api/case/{case_id}`, `POST /api/evaluate` (the old single `rating`/`critique`/`recommendations`/`source_slides` shape), and the frontend's `mockProjectState.ts`. Nothing in the running app depends on them anymore; `backend/cases_data.py` still holds the old Blazar/Basil content only because `chat_engine.py`'s legacy `case_id` mode (above) still imports it.

**Known gaps**: no manual-transcript-paste endpoint yet — an audio artifact that lands in `'Transcript Needed'` status (GCS/Speech-to-Text unavailable, unconfigured, or an unsupported format) has no way through the API to be completed — the async ingestion pipeline (2026-09-02) didn't close this; it only made the deployed processor's `GCS_TRANSCRIBE_BUCKET` actually get set (Terraform), so audio has a chance of transcribing at all in a deployed env. A separate, non-REST endpoint lives on `backend/processor_main.py` (`POST /` — the Eventarc target, private, invoker-restricted to the processor SA); it isn't part of the main app's API surface. `admin_auth.py`'s stopgap shared-token gate (`ADMIN_API_TOKEN`) still guards `/api/admin/settings` instead of the real `require_admin` dependency everything else above uses.

# Part 5: Current Status & Roadmap

**As of 2026-09-02: Phase 0/A/B/C, Backend API Integration, Frontend GUI Overhaul, Admin UI, Framework Authoring Mode, and the async artifact-ingestion pipeline are all done in code** (the pipeline is built but **not deployed** — see below and Part 6). `backend/main.py` no longer runs any hardcoded case-study critic — the old `/api/evaluate`/`CASES_DATA` path was retired 2026-08-31 once `frontend-react/` was fully wired to the real `/api/projects/*`/`/api/auth/*`/`/api/chat/*` backend. What remains **not** built: the Guided Learning Flow (baseline calibration, adaptive difficulty, case-study reveal, corpus-relative depth signal, Start/Stop/Continue — see Part 1), and production deployment infrastructure (a GCP Cloud Run plan exists but only its CI test workflow is actually built — see Part 6). `backend/database.py` and `backend/rag_engine.py` have been migrated off SQLite + flat-file storage onto Neon Postgres + `pgvector` (Phase 0) — see the Foundational Work section of the Roadmap.

**Scope grew twice more on 2026-08-24**: first, a gap was identified — there was no way for a consultant to bring a customer's own enterprise artifacts into an engagement, and no real user/auth model at all. A new design ([spec](docs/superpowers/specs/2026-08-24-users-projects-engagement-kb-design.md)) adds Users, Projects (replacing `client_case_id`), and a per-project Engagement Knowledge Base, in phases (0: DB platform, A: Auth, B: Projects, C: Engagement KB). Second, the database platform itself was decided: Neon Postgres + `pgvector` ([spec](docs/superpowers/specs/2026-08-24-neon-postgres-pgvector-design.md)), replacing SQLite + flat files for the *entire* data layer, including the already-implemented `processes`/`stages`/`questions`/`guidance` tables. **Phase 0 of that migration (the DB platform itself, plus the Framework Knowledge Base) has since been built and is done.** A same-day stakeholder review meeting also produced the Guided Learning Flow design (Part 1). All of this **precedes** the pre-existing "Database Layer Overhaul" and "Backend API Integration" roadmap items — see the roadmap for how they've been revised.

**Phase A (Users & Auth) landed 2026-08-28**: a real `users` table, `POST /api/auth/register`/`login`, `GET /api/auth/me`, and a `get_current_user` FastAPI dependency (`backend/auth.py`, `backend/users_db.py`) — see `docs/superpowers/plans/2026-08-28-phase-a-users-auth.md`.

**Phase B (Projects) landed 2026-08-28**: `projects`/`project_members` tables, `backend/projects_db.py`, `require_admin`/`require_project_role`/`require_active_project` dependencies, and `/api/projects` create/list/detail/update/activate — see `docs/superpowers/plans/2026-08-28-phase-b-projects.md`. At the time this phase landed, `CASES_DATA`/`GET /api/cases`/`GET /api/case/{case_id}` were deliberately left untouched (they've since been retired — see Part 4) and `POST /api/projects/{id}/members` didn't exist yet (it now does — added 2026-08-31, see Part 4). The `responses` table was DDL only when this phase landed — Backend API Integration below started reading/writing it. `admin_auth.py`'s stopgap gate is still untouched — a real `require_admin` exists and is used everywhere else, but `/api/admin/settings` specifically still uses the older token gate (see Part 4's Known gaps).

**Phase C (Engagement Knowledge Base) landed 2026-08-28**: `project_artifacts`/`project_kb_chunks` tables, `backend/project_artifacts_db.py`, `backend/project_knowledge_base.py` (parsing, chunking, embedding, synchronous `ingest_artifact` orchestrator), and `/api/projects/{id}/artifacts` upload/list/delete — see `docs/superpowers/plans/2026-08-28-phase-c-engagement-kb.md`. Audio transcription (originally AWS Transcribe, migrated to Google Speech-to-Text 2026-09-01 — see Part 6) gracefully degrades to a `'Transcript Needed'` artifact status when the transcription bucket isn't configured or the provider is otherwise unavailable — never `'Failed'` for that specific case, mirroring the codebase's existing graceful-degradation philosophy; an artifact that produces no extractable text at all IS marked `'Failed'`, though (a fix applied during implementation review — the original plan would have silently marked it `'Indexed'` with nothing actually searchable). Uploads are capped at 50MB (also a review-driven fix — the original plan had no size limit on this, the first untrusted-file-upload endpoint in the codebase). A manual-transcript-paste endpoint to complete the `'Transcript Needed'` fallback loop still doesn't exist. Original uploaded file bytes are never persisted anywhere — only the extracted/transcribed text survives, embedded into `project_kb_chunks`.

**Backend API Integration landed 2026-08-28**: `backend/process_db.py` (`GET /api/process/{id}`), `RagEngine.search_merged` + `RagEngine.generate_comparative_benchmarks` (two new methods on the existing `RagEngine`, no second embedding model or LLM abstraction), `backend/responses_db.py` (first code to read/write the Phase-B `responses` table), `backend/brief.py`, and three endpoints — `POST /api/projects/{id}/evaluate`, `POST /api/projects/{id}/responses`, `GET /api/projects/{id}/brief` — see `docs/superpowers/plans/2026-08-28-backend-api-integration.md`. **Built as new, additive endpoints at the time** (the roadmap's literal wording called for overhauling `/api/evaluate` itself, but that would have broken the still-untouched-at-the-time frontend) — the cutover this deferred happened three days later, see Frontend GUI Overhaul below. Three real bugs were found and fixed during implementation review: `generate_comparative_benchmarks` now falls back to fixed local content if the LLM returns valid-but-incomplete JSON (missing a benchmark level), not just on a provider error; `responses_db.save_response`'s upsert now uses `COALESCE` per column instead of unconditional overwrite — the original would have silently wiped a saved answer the first time a self-evaluation was saved as a separate call (verified live against Postgres, both before and after the fix); and `POST /api/projects/{id}/responses` now validates cross-process `question_id` ownership, which the plan's own Global Constraints required for both new endpoints but its Task 7 spec had omitted.

**Frontend GUI Overhaul and Admin UI both landed 2026-08-31**: `frontend-react/` was wired end-to-end to the real backend — login/register, project dashboards (`GET /api/projects`), a New Project form, a project setup page (industry context, activate, artifacts, members, Framework editor), a client hub, and the chat interview page rendering project-scoped Level 1/2/3 benchmarks as a split-screen comparison with source references, a self-evaluation dropdown, and Download Brief. `CASES_DATA`, `GET /api/cases`, `GET /api/case/{case_id}`, `POST /api/evaluate`, and the frontend's `mockProjectState.ts` were **retired**, not left running alongside the new flow (commit `ec3b18a`, "now that the real backend is fully wired"). Separately, an `/admin` page (Users tab, Projects tab) and `POST/GET/PATCH/DELETE /api/projects/{id}/members[/{user_id}]` landed the same day — see `docs/superpowers/specs/2026-08-31-admin-ui-design.md` and `docs/superpowers/plans/2026-08-31-admin-ui.md`. A large-upload-freezes-the-backend bug (synchronous ingestion blocking the event loop) was found and fixed the same day too (`run_in_threadpool` in `backend/main.py`).

**Framework Authoring Mode landed 2026-09-01**: each project now owns its own framework. The seeded "Aditya Birla Brand Compass V2" process is flagged read-only `is_template`; `POST /api/projects` clones it into a fresh process (named `"{project.name} Framework"`) and points the project at the clone, and a one-time idempotent migration in `database.init_db` re-points existing projects the same way. A new `questions.sequence_order` column (migration + backfill) powers move-up/down. New `backend/framework_db.py` (template lookup, clone, stage/question CRUD + guidance upsert + reordering) and seven Consultant-only endpoints under `/api/projects/{id}/framework` (get, add/patch/delete stage, add/patch/delete question). Evaluation/chat/brief are untouched — they already read `project.process_id`. Frontend: a "Framework" editor on the consultant's project setup page, and the New Project form no longer hardcodes a process id. See `docs/superpowers/specs/2026-09-01-framework-authoring-mode-design.md` and `docs/superpowers/plans/2026-09-01-framework-authoring-mode.md`.

**The async artifact-ingestion pipeline landed 2026-09-02 — in code only, not deployed** (same "built, not deployed" status this file already uses for the GCP Cloud Run plan in Part 6; nothing in this repo has a live GCP deployment). What's built: `backend/gcs_artifact_storage.py` (raw/processed/failed object staging and moves), `backend/processor_main.py` (a second deployable FastAPI service, the Eventarc target), a dual-mode `POST /api/projects/{id}/artifacts` and a GCS-cascading `DELETE` (Part 4), `.md`/`.xlsx` support and the `Queued` status/`gcs_object_path` column with their idempotent migration, a status-polling project setup UI, and `infra/terraform/artifact-pipeline/` — the repo's first Terraform module (bucket, Eventarc trigger, private Cloud Run service, service accounts, prefix-conditioned IAM). A final whole-branch review then fixed seven cross-task integration bugs the per-task reviews couldn't see, chief among them: **Eventarc's GCS-direct triggers have no object-name-prefix filter** (the spec assumed one), so the processor's own `processed/`/`failed/` writes re-trigger it — it now returns `200 skipped` on any non-`raw/` payload instead of 500ing into a multi-day retry stream; the processor treats `Uploaded` as well as `Queued` as processable (the upload endpoint sets `Queued` *after* the GCS write, so an event delivered in that window would otherwise strand the artifact); an exception mid-processing now moves the object to `failed/` and marks the row `Failed` rather than leaving it stuck at `Processing` forever; the delete endpoint treats a GCS `NotFound` as success; the Cloud Run service got `2Gi`/`2` CPU and a `900s` timeout (it loads a `SentenceTransformer`) plus `GCS_TRANSCRIBE_BUCKET`; and `cosmos-backend-sa` got `objectAdmin` rather than create-only `objectCreator` on `raw/`, without which a stuck artifact could never be deleted. See `docs/superpowers/specs/2026-09-02-artifact-ingestion-pipeline-design.md` and `docs/superpowers/plans/2026-09-02-artifact-ingestion-pipeline.md`.

**The Chat Interview Screen UI/UX Redesign landed 2026-09-10**: the chat interview screen (`frontend-react/app/client/case/[caseId]/chat/`) moved from the earlier dark glassmorphism theme to a "Light Professional" palette, scoped entirely to a new route-local `chat.module.css` (no shared/dark tokens touched). New: a persistent stage-progress sidebar (`GET /api/projects/{id}/stage-progress`, Part 4 — backed by `backend/process_db.get_stage_summary` and rendered by `components/chat/StageSidebar.tsx`, marking each stage done/current/upcoming from a cumulative sum of `question_count` against `current_level_index`), a true side-by-side Level 1/2/3 benchmark comparison grid (`ChatMessageBubble`'s `benchmark` case restructured, only the live/unanswered benchmark turn interactive), and click-to-rate self-evaluation replacing the old dropdown (clicking a level card now sets the `self_evaluation_status` directly; the accompanying note became optional). A data-loss bug surfaced in the final whole-branch review — making the note optional meant a blank note could silently erase a previously-saved one, since `responses_db.save_response`'s `COALESCE`-based upsert only preserves a prior value against SQL `NULL`, not an empty string, and the adaptive-difficulty follow-up loop can revisit the same question's self-rating more than once — fixed the same day in `backend/chat_engine.py` (`self_evaluation_notes=(user_content or None)`), the one deliberate, user-approved exception to this work's own "chat_engine.py/responses_db.py unchanged" scope. See `docs/superpowers/specs/2026-09-09-chat-interview-ui-redesign-design.md` and `docs/superpowers/plans/2026-09-09-chat-interview-ui-redesign.md`.

**A pluggable multi-provider LLM layer** (`backend/llm_providers/`) was added ahead of Phase A/B — see `docs/superpowers/specs/2026-08-25-production-deployment-design.md` and `docs/superpowers/plans/2026-08-25-llm-provider-abstraction.md`. Its admin settings endpoint still uses the stopgap shared-token gate (`ADMIN_API_TOKEN`); Phase B's real `require_admin` dependency could replace it, but hasn't yet.

**A chat-style interview backend** (`backend/chat_engine.py`, `chat_sessions`/`chat_messages` tables) was added ahead of the frontend work that would consume it — see `docs/superpowers/specs/2026-08-26-chat-style-interview-design.md` and `docs/superpowers/plans/2026-08-26-chat-style-interview.md`. It's now the live, frontend-facing evaluation path (see Part 2 and Part 4) — `chat_sessions` gained a nullable `project_id` column (2026-08-31) so every session the frontend creates is project-scoped.

**The frontend was migrated to Next.js (React, TypeScript) on 2026-08-27** (`frontend-react/`, replacing the old vanilla HTML/CSS/JS frontend) — see `docs/superpowers/plans/2026-08-26-react-frontend-migration.md`. Users/Projects/Auth were initially stubbed with a localStorage-backed mock; that mock was removed 2026-08-31 once Frontend GUI Overhaul (above) wired everything to the real backend.

A test bed now exists (`tests/`, 379 pytest tests, run via `pytest` from the repo root) covering essentially every module named above; see Part 6. The pre-migration API contract test suite once planned against `CASES_DATA`/`/api/evaluate` is moot — that API no longer exists.

Full checklist (Users/Projects/Engagement KB phases, DB layer, backend API, frontend GUI, production deployment): [Roadmap](documentation/product/roadmap.md). Don't assume anything in that checklist is done without checking it — it's a live document, check it before starting related work.

# Part 6: Development Workflow

**Setup & run**: see [Quick Start](documentation/guides/quick-start.md) for full steps. Summary:
```bash
cd backend && python -m venv venv && <activate> && pip install -r requirements.txt
# copy .env.example to .env at the repo root and set DATABASE_URL first — see Quick Start
python database.py   # creates schema + seeds process/stage/question data in Neon
python main.py        # serves API + frontend at http://localhost:8000; also builds the Framework Knowledge Base index on first run
```

**Tests**: a test bed exists now (`tests/`, 379 tests) covering the LLM Provider Abstraction modules, the chat-style interview modules (`chat_sessions`, `chat_engine`, `chat_endpoints`), the Phase A auth modules (`users_db`, `auth`, `/api/auth/*` endpoints), the Phase B project modules (`projects_db`, the new `auth` dependencies, `/api/projects/*` endpoints), the Phase C Engagement KB modules (`project_artifacts_db`, `project_knowledge_base`, `/api/projects/*/artifacts*` endpoints), the Backend API Integration modules (`process_db`, `responses_db`, `brief`, `RagEngine.search_merged`/`generate_comparative_benchmarks`, the new `/evaluate`/`/responses`/`/brief` endpoints), the Framework Authoring Mode modules (`framework_db`, `/api/projects/*/framework/*` endpoints), the Baseline Calibration modules (`calibration_db`, `/api/projects/*/framework/calibration*` endpoints), and the async ingestion pipeline modules (`gcs_artifact_storage`, `processor_main`, the `.md`/`.xlsx` extractors, the dual-mode upload/delete paths) — run `pytest` from the repo root. The Terraform module is checked separately with `terraform -chdir=infra/terraform/artifact-pipeline validate` and `... fmt -check -recursive` (no CI job runs these yet). A previously-tracked "broader pre-migration API contract test bed" (case-study endpoints, `/api/evaluate`'s response shape) is no longer a planned item — that API was retired 2026-08-31, so there's nothing left to write contract tests against; `documentation/testing/test-strategy.md` still describes it and needs updating.

**CI**: `.github/workflows/ci.yml` runs the full `pytest` suite on every push/PR to `main` — this is the only piece of the GCP production deployment plan (below) that's actually been built.

**Production deployment**: a GCP Cloud Run deployment was decided and specced on 2026-08-25 (`docs/superpowers/specs/2026-08-25-production-deployment-design.md`, `docs/superpowers/plans/2026-08-25-gcp-deployment-infrastructure.md`) — GCP, not AWS, chosen specifically to drop the AWS Bedrock LLM dependency (superseded by the pluggable multi-provider LLM layer above) — but **only the CI test workflow (Task 5) has actually been built**. The Dockerfile, `/healthz` route, deploy workflow, GCP project bootstrap (Artifact Registry, service accounts, Secret Manager, Workload Identity Federation), and Cloud Monitoring alerts (Tasks 1-4, 6-7) are all still just plan steps, not done. There is no automated deployment today — the app runs locally only (see Setup & run above). The async ingestion pipeline's own Terraform module (`infra/terraform/artifact-pipeline/`, 2026-09-02 — the repo's first IaC) is written to stand alone and compose with that plan later; it is validated/`fmt`-clean but **has never been applied to a GCP project**, so it doesn't change the "nothing is deployed" status above. The codebase is not otherwise AWS-free yet either: Phase C's audio transcription originally used AWS Transcribe/`boto3` (added 2026-08-28, after the GCP decision, and never reconciled with it until now) — migrated to Google Speech-to-Text/`google-cloud-speech` on 2026-09-01 (see Part 3 above), closing that gap. No other AWS dependency remains in the codebase.
