# Product Roadmap — Cosmos Strategic Capability Platform

**Last Updated:** 2026-08-28

This is the living status document for the project: what's been decided, what's built, and what's next. It replaces the one-time `plan/task.md` checklist and the forward-looking sections of `plan/implementation_plan.md`.

## Current Phase: Insights POC — Foundational Work + Backend API Integration Complete, Frontend Cutover Not Started

The project has fully specified the pivot from a static "Q&A critic" (hardcoded Blazar/Basil case studies, single rating/critique/recommendations output) to an **interactive process authoring and execution engine** (the "Framework Factory") backed by a configurable process/stage/question schema and Level 1/2/3 comparative benchmark generation. See `documentation/architecture/overview.md` for the target architecture and `documentation/development/technical-spec.md` for the schema and API contract.

**Phases 0/A/B/C and Backend API Integration are all complete — see the Foundational Work and Migration Checklist sections below.** Frontend GUI Overhaul has not been implemented yet. The running code (`backend/main.py`) still reflects the old design for its *currently live* evaluation flow: an in-memory `CASES_DATA` dict with the Blazar/Basil cases still serves `/api/evaluate` and the current frontend, unchanged and untouched. The new project-scoped comparative-benchmark flow (Level 1/2/3 benchmarks, merged Framework + Engagement KB retrieval, response persistence, brief compilation) exists and works, fully tested — but as **separate, additive endpoints** under `/api/projects/{id}/...`, not wired into `/api/evaluate` or the frontend yet. `backend/database.py` and `backend/rag_engine.py` run on Neon Postgres + `pgvector` rather than SQLite + a flat file; real login/registration, project provisioning, and Engagement KB uploads all exist via `/api/auth/*`, `/api/projects/*`.

**2026-08-24 stakeholder review meeting** (transcript: `archives/Meeting transcript 24Aug.txt`) substantially detailed the intended Insights-module learning experience and confirmed the underlying business-problem framing from the BRD. It also surfaced the System Flow gap below and prompted the Neon Postgres decision. See `documentation/product/functional-spec.md` for the resulting design.

## Foundational Work: Database Platform, Users, Projects & Engagement Knowledge Base

Two gaps surfaced after the original specs were written: (1) there was no concept of a real user, and no way for a consultant to bring a customer's own enterprise artifacts into an engagement for retrieval during a workshop, and (2) the SQLite + flat-JSON-file storage pattern doesn't scale and isn't the cheapest option available. Full designs: [Users/Projects/Engagement KB Spec](../../docs/superpowers/specs/2026-08-24-users-projects-engagement-kb-design.md) and [Neon Postgres + pgvector Spec](../../docs/superpowers/specs/2026-08-24-neon-postgres-pgvector-design.md).

This **supersedes and precedes** the "Database Layer Overhaul" and "Backend API Integration" items below — it formalizes the ad hoc `client_case_id` string into a first-class `Project` entity (Cosmos's equivalent of AWS MAP's Opportunity), adds real auth and per-project role membership, moves the entire data layer onto Neon Postgres + `pgvector`, and delivers the `responses` table's `self_evaluation_notes`/`self_evaluation_status` migration as part of the same schema change.

Two distinct knowledge bases result from this design, both `pgvector`-backed in the target state:
- **Framework Knowledge Base**: the shared Cosmos methodology materials. **Done as of Phase 0** — migrated from `archives/` → `data/vector_db.json` (flat file) into the `framework_kb_chunks` table (Neon Postgres + `pgvector`, HNSW-indexed).
- **Engagement Knowledge Base** (new, not yet built): a per-project index of the *customer's own* documents, meeting audio, and case studies (external, internal, hidden resolution — tagged by `purpose`), uploaded by the Consultant and automatically blended into retrieval alongside the Framework Knowledge Base during evaluation.

Roles are `SystemAdmin` (global — creates projects, assigns the leading Consultant), `Consultant` (per-project — preps the engagement, activates it), and `ClientUser` (per-project — works the learning flow, blocked until the project is `Active`). `Owner`/`Reviewer`/`Peer` from the original design are deferred, not abandoned.

- [x] **Phase 0 — Database Platform**: stand up a Neon project, `CREATE EXTENSION vector`, migrate `processes`/`stages`/`questions`/`guidance` DDL from SQLite to Postgres, rebuild the Framework Knowledge Base into `framework_kb_chunks`. Everything below depends on this. **Scope note**: the legacy SQLite `responses` table (`id`, `question_id`, `client_case_id`, `submitted_text`, `status`, `rating`, `critique`, `recommendations`, `updated_at`) was dropped, not migrated — no `responses` table exists in Postgres today. It's superseded by Phase B's `project_id`-based redesign below, so recreating the old shape now just to replace it again in Phase B would be wasted work.
- [x] **Phase A — Users & Auth**: `users` table (incl. `is_admin`), register/login, JWT issuance/verification, `get_current_user` dependency. **Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-phase-a-users-auth.md`. `require_admin` was reassigned to Phase B in that plan (it depends on the `is_admin` flag being checked in the context of project creation, which didn't exist until Phase B) — not built here, but now built as part of Phase B below. `admin_auth.py`'s stopgap shared-token gate is still untouched — Phase B's `require_admin` dependency exists now but hasn't been wired into `/api/admin/settings`; that replacement is still a future decision, not yet made. `get_current_user`/`require_admin`/`require_project_role`/`require_active_project` are not yet wired into any pre-existing endpoint (`/api/evaluate`, `/api/chat/sessions`, etc.) — those stay open/unauthenticated until Backend API Integration introduces `project_id`-scoped access control.
- [x] **Phase B — Projects**: `projects` (incl. `industry_context`, `status` starting at `Draft`) + `project_members` tables, `backend/projects_db.py`, `require_admin`/`require_project_role`/`require_active_project` dependencies, `POST /api/projects` (SystemAdmin-only), `GET /api/projects` (list), `GET /api/projects/{id}` (detail), `PATCH /api/projects/{id}`, `POST /api/projects/{id}/activate`, and the `responses` table DDL (`project_id`-based — no prior `responses` table exists to migrate from, since Phase 0 dropped the legacy one; see above). **Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-phase-b-projects.md`. **Deviates from this bullet's original wording in two ways, both deliberate**: `CASES_DATA`/`GET /api/cases`/`GET /api/case/{case_id}` were **not** removed (doing so now would break the untouched React frontend's case-selection flow — removal is deferred to Frontend GUI Overhaul, once the frontend is cut over to `/api/projects`); and `POST /api/projects/{id}/members` was **not** built (the initial Consultant is assigned atomically inside `POST /api/projects`, which was sufficient to build and test every dependency in this phase — adding further members, in particular any `ClientUser`, is a known gap left for a follow-up). The `responses` table was DDL-only when this phase landed — Backend API Integration (below) is the first code to read/write it.
- [x] **Phase C — Engagement Knowledge Base**: `project_artifacts` table (incl. `purpose` tagging for case studies) + `project_kb_chunks` `pgvector` table (HNSW-indexed, mirroring `framework_kb_chunks`), `backend/project_artifacts_db.py`, `backend/project_knowledge_base.py` ingestion pipeline (PDF/DOCX/PPTX/TXT parsing, AWS Transcribe audio transcription with graceful degradation to a `'Transcript Needed'` status when AWS isn't configured, chunking, embedding via the existing `SentenceTransformer`), and three endpoints — `POST` (upload, Consultant-only, 50MB cap), `GET` (list, any project member), `DELETE` (Consultant-only) on `/api/projects/{id}/artifacts[/{artifact_id}]`. **Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-phase-c-engagement-kb.md`. **Deviates from this bullet's original wording in two ways, both deliberate**: the merged retrieval was **not** built into `/api/evaluate` itself — Backend API Integration (below) added it as a separate `RagEngine.search_merged` method powering a new endpoint instead, since `/api/evaluate` stays untouched; and the **Engagement Documents frontend panel** was **not** built — this phase is backend-only, per its plan's explicit scope. `POST /api/projects/{id}/members` still doesn't exist (a pre-existing Phase B gap, not reopened here) and there's no manual-transcript-paste endpoint yet to complete the `'Transcript Needed'` fallback loop — both are known, named gaps for a follow-up plan. Original uploaded file bytes are never persisted anywhere (only the extracted/transcribed text survives, embedded into `project_kb_chunks`) — durable original-file storage was left undecided at the design level.

## Guided Learning Flow (new — from the Aug 24 stakeholder meeting)

Full design: [Functional Spec §2.3](functional-spec.md#23-guided-learning-flow-clientuser). Builds on Phase C above (case studies are Engagement KB artifacts). Not yet scoped into a phase/build order — listed here so it isn't lost, tracked as its own checklist:

- [ ] Baseline concept calibration step (scored against the org's own definitions, not generic correctness).
- [ ] Per-question theory + externally-deducible examples + serious/fun exercise pair.
- [ ] Adaptive question difficulty (probe-then-escalate, with guardrails). **Sharpened 2026-08-26** (`archives/Meeting Min 26Aug.txt`): the master/anchor question per level must be fixed, human-authored Consultant IP — never AI-reworded — with only the post-answer drill-down follow-ups being AI-generated, looping until sufficient depth is reached ("it will not move till you have done justice to the work"). **This is a known correction needed in already-shipped code**: `backend/chat_engine.py`'s `_ask_question` (from the 2026-08-26 chat-style interview backend) currently has the AI conversationally rephrase the canonical question rather than presenting it verbatim, and has no probe-then-escalate loop at all — both need addressing when this checklist item is scheduled.
- [ ] Consultant preview/edit of AI-facing question content before a ClientUser sees it (from the same meeting) — largely superseded by the point above once master questions are Consultant-authored directly (via Framework Authoring Mode, see "Beyond the POC" below) rather than AI-generated-then-reviewed; revisit whether a separate review step is still needed once that's designed.
- [ ] Actionability check on vague-but-eloquent answers.
- [ ] Keyword-agnostic answer mapping (map jargon-free answers back to framework terms).
- [ ] Case study resolution flow: hidden reveal + limited AI debate + seeded provocations, for both external and internal case studies.
- [ ] Self-evaluation with a corpus-relative depth signal — **note**: this requires querying across all historical `responses`, a capability not yet designed at the data-model level (flagged as an open gap in `architecture/overview.md` §4).
- [ ] Start/Stop/Continue reflection at module completion.
- [ ] Human escalation path (~20 min live discussion), by exception.

## Migration Checklist

### 1. Database Layer Overhaul — superseded by Phase A/B above
The schema goals here (drop `rating`/`critique`/`recommendations`, add `self_evaluation_notes`/`self_evaluation_status`) are delivered as part of the Users/Projects/Engagement KB spec's `responses` table redesign — see the spec linked above for the full DDL. This item is no longer tracked separately.

### 2. Backend API Integration
- [x] Connect `backend/main.py` to Neon Postgres:
  - Query **projects** dynamically — `GET /api/projects/{id}` (Phase B) already does this; this item adds `GET /api/process/{process_id}` for DB-backed stage/question retrieval (`backend/process_db.py`).
  - DB routes to get stages and questions by process ID — done via `GET /api/process/{process_id}`, nesting stages → questions → guidance.
- [x] Comparative-benchmark evaluation, delivered as a **new, additive** endpoint rather than an overhaul of the existing one (see deviation note below):
  - `RagEngine.generate_comparative_benchmarks` generates Level 1/2/3 comparative responses (a new method, not a rewrite of the existing single-rating prompt).
  - New response payload shape (`{question_id, level_1, level_2, level_3, source_chunks}`) — on the new `POST /api/projects/{project_id}/evaluate` endpoint, not on `/api/evaluate` itself.
  - `RagEngine.search_merged` merges retrieval across the Framework Knowledge Base and the current project's Engagement Knowledge Base (Phase C), source-tagged, excluding `case_study_resolution`-purpose chunks.
- [x] `POST /api/projects/{project_id}/responses` (`backend/responses_db.py`) stores submitted text, self-evaluation notes, and self-evaluation status — upsertable per `(question_id, project_id)` via `COALESCE` semantics, so a "save the answer" call followed by a separate "save the self-evaluation" call never wipes the other's data.
- [x] `GET /api/projects/{project_id}/brief` (`backend/brief.py`) outputs a compiled markdown summary brief (no HTML/PDF rendering — a deliberately simple template, per this item's own "don't over-engineer" scope note).

**Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-backend-api-integration.md`. **Deviates from this bullet's original wording in one deliberate, controller-directed way**: rather than overhauling `POST /api/evaluate` in place, every deliverable above was built as **new, additive endpoints** under `/api/projects/{project_id}/...` and `/api/process/{process_id}`. `POST /api/evaluate`, its `rating`/`critique`/`recommendations`/`source_slides` response shape, and `CASES_DATA`/`GET /api/cases`/`GET /api/case/{case_id}` are all **untouched** — the current React frontend still depends on them and this item doesn't touch the frontend. The actual cutover (pointing the frontend at the new endpoints and retiring the old ones) is deferred to Frontend GUI Overhaul below. Three real bugs were found and fixed during implementation review: an LLM response missing a benchmark level silently returned incomplete instead of falling back; the responses upsert unconditionally overwrote every column (including with `NULL`), which would have silently wiped a saved answer the first time a self-evaluation was saved separately; and `POST /api/projects/{project_id}/responses` was missing the cross-process `question_id` validation this plan's own Global Constraints required (mirrored from the evaluate endpoint).

### 3. Frontend GUI Overhaul
**The vanilla-JS `frontend/` was replaced by a Next.js (React, TypeScript) frontend in `frontend-react/` on 2026-08-27** (see `docs/superpowers/plans/2026-08-26-react-frontend-migration.md`) — it covers all three roles and the chat-style interview flow, but Projects/Auth (Phase A/B) are still mock/`localStorage`-backed, and the items below were explicit Non-Goals of that migration, not delivered by it. **All backend endpoints these items need now exist and are unblocked** (Phase A/B/C + Backend API Integration all landed 2026-08-28) — this is purely frontend work from here:
- [ ] Update `frontend-react/` to fetch projects, stages, and questions dynamically from the backend (`GET /api/projects`, `GET /api/projects/{id}`, `GET /api/process/{id}`) rather than relying on the mock/`localStorage`-backed project state.
- [ ] Build the split-screen comparison UI, backed by `POST /api/projects/{id}/evaluate`:
  - User's answer side-by-side with RAG context slides, each labeled by source ("Framework Reference" vs. "Customer Document") — `source_chunks` in the endpoint's response already carries this tag.
  - Level 1/2/3 exemplary comparative answers — already in the endpoint's response (`level_1`/`level_2`/`level_3`).
  - Self-Evaluation Notes input and a status selector (Needs Work, Satisfactory, Strong), saved via `POST /api/projects/{id}/responses`.
- [ ] Add a "Download Brief" button, backed by `GET /api/projects/{id}/brief` (returns compiled markdown).
- [ ] Add a login screen, a project dashboard (replacing the hardcoded case-select screen), and an "Engagement Documents" panel per project (Phase C) — backed by `/api/projects/{id}/artifacts`.
- [ ] Once the above land, cut `/api/evaluate` over to the new endpoints and retire it along with `CASES_DATA`/`GET /api/cases`/`GET /api/case/{case_id}` — this was deliberately deferred by both Phase B/C and Backend API Integration to avoid breaking the app mid-build; it's this item's responsibility to complete the cutover.
- [ ] Add the Guided Learning Flow screens: baseline calibration, case study resolution reveal, Start/Stop/Continue reflection (see Guided Learning Flow checklist above).
- [ ] Refine `frontend-react/`'s styling (dark/light tokens, Outfit/Inter typography, loading skeletons, responsive split columns).

## Beyond the POC (not yet scoped)

The BRD frames this POC as validation before a full multi-tenant build. Not yet designed:
- Framework Authoring Mode (admin/consultant interface to define new processes, stages, and questions beyond the seeded Brand Compass configuration). **Note (2026-08-26 meeting)**: whatever this authors must be treated as fixed Consultant IP going forward — the master/anchor question text itself should never be regenerated or reworded by the AI at runtime; only follow-up drill-down questions are AI-generated. See the Guided Learning Flow checklist above.
- `Owner`/`Reviewer`/`Peer` client-side role distinctions (deferred in favor of a single `ClientUser` role — see the Users/Projects/Engagement KB spec's Revision section).
- Automatic mapping of a `questions.owner_role` string (e.g. "CMO") to a specific project member — for now, any `ClientUser` can answer any question.
- SSO / enterprise identity (Azure AD, Cognito, etc.) — the near-term auth design (Phase A above) is deliberately simple, built-in email/password.
- Multi-**firm** isolation (multiple consulting firms sharing one deployment). Note this is narrower than it used to be: per-*project* isolation (one customer engagement's data kept separate from another's) is now addressed by the Foundational Work above, once built, via `pgvector` row-level `project_id` scoping — what remains open is isolating separate consulting *firms* from each other on a shared instance.
- **Four additional product modules** beyond Insights/Capability Building — management process building, organization transparency building, performance & potential evaluation, and DIY consulting — sharing the same underlying corpus but with dramatically different user experiences per the Aug 24 meeting. A follow-up stakeholder call is scheduled to go deeper into these; see `documentation/product/functional-spec.md` §5 for the framing captured so far.
- Neon Object Storage / Functions / AI Gateway — explicitly out of scope per the Neon spec; original uploaded file storage (as opposed to their vector embeddings) is still an open question, not decided.
