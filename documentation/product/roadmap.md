# Product Roadmap — Cosmos Strategic Capability Platform

**Last Updated:** 2026-09-02

This is the living status document for the project: what's been decided, what's built, and what's next. It replaces the one-time `plan/task.md` checklist and the forward-looking sections of `plan/implementation_plan.md`.

## Current Phase: Insights POC — Full-Stack Feature-Complete Through Framework Authoring Mode; Production Deployment Not Started

The project has fully specified the pivot from a static "Q&A critic" (hardcoded Blazar/Basil case studies, single rating/critique/recommendations output) to an **interactive process authoring and execution engine** (the "Framework Factory") backed by a configurable process/stage/question schema and Level 1/2/3 comparative benchmark generation. See `documentation/architecture/overview.md` for the target architecture and `documentation/development/technical-spec.md` for the schema and API contract.

**Phases 0/A/B/C, Backend API Integration, Frontend GUI Overhaul, Admin UI, Framework Authoring Mode, and the async artifact-ingestion pipeline are all complete in code** — see the Foundational Work and Migration Checklist sections below. **Only Production Deployment Infrastructure (see that section below) has not been implemented** — the app runs locally only, there is no live or automated deployment (only a CI test workflow exists, and the ingestion pipeline's Terraform module has never been applied). The old hardcoded evaluation flow is **gone, not just superseded**: `CASES_DATA`, `GET /api/cases`, `GET /api/case/{case_id}`, and `POST /api/evaluate` were retired 2026-08-31 once `frontend-react/` was fully wired to the real backend. The live, frontend-facing evaluation flow today is the chat interview (`POST /api/chat/sessions*`, project-scoped), backed by the Level 1/2/3 comparative-benchmark pipeline (merged Framework + Engagement KB retrieval, response persistence, brief compilation) built during Backend API Integration. `backend/database.py` and `backend/rag_engine.py` run on Neon Postgres + `pgvector` rather than SQLite + a flat file; real login/registration, project provisioning, per-project framework authoring, project membership management, an admin console, and Engagement KB uploads all exist and are wired into `frontend-react/` via `/api/auth/*`, `/api/projects/*`, `/api/admin/*`.

**2026-08-24 stakeholder review meeting** (transcript: `archives/Meeting transcript 24Aug.txt`) substantially detailed the intended Insights-module learning experience and confirmed the underlying business-problem framing from the BRD. It also surfaced the System Flow gap below and prompted the Neon Postgres decision. See `documentation/product/functional-spec.md` for the resulting design.

## Foundational Work: Database Platform, Users, Projects & Engagement Knowledge Base

Two gaps surfaced after the original specs were written: (1) there was no concept of a real user, and no way for a consultant to bring a customer's own enterprise artifacts into an engagement for retrieval during a workshop, and (2) the SQLite + flat-JSON-file storage pattern doesn't scale and isn't the cheapest option available. Full designs: [Users/Projects/Engagement KB Spec](../../docs/superpowers/specs/2026-08-24-users-projects-engagement-kb-design.md) and [Neon Postgres + pgvector Spec](../../docs/superpowers/specs/2026-08-24-neon-postgres-pgvector-design.md).

This **supersedes and precedes** the "Database Layer Overhaul" and "Backend API Integration" items below — it formalizes the ad hoc `client_case_id` string into a first-class `Project` entity (Cosmos's equivalent of AWS MAP's Opportunity), adds real auth and per-project role membership, moves the entire data layer onto Neon Postgres + `pgvector`, and delivers the `responses` table's `self_evaluation_notes`/`self_evaluation_status` migration as part of the same schema change.

Two distinct knowledge bases result from this design, both `pgvector`-backed in the target state:
- **Framework Knowledge Base**: the shared Cosmos methodology materials. **Done as of Phase 0** — migrated from `archives/` → `data/vector_db.json` (flat file) into the `framework_kb_chunks` table (Neon Postgres + `pgvector`, HNSW-indexed).
- **Engagement Knowledge Base**: a per-project index of the *customer's own* documents, meeting audio, and case studies (external, internal, hidden resolution — tagged by `purpose`), uploaded by the Consultant and automatically blended into retrieval alongside the Framework Knowledge Base during evaluation. **Done as of Phase C** (backend) **and Frontend GUI Overhaul** (upload/list/delete UI on the project setup page).

Roles are `SystemAdmin` (global — creates projects, assigns the leading Consultant), `Consultant` (per-project — preps the engagement, activates it), and `ClientUser` (per-project — works the learning flow, blocked until the project is `Active`). `Owner`/`Reviewer`/`Peer` from the original design are deferred, not abandoned.

- [x] **Phase 0 — Database Platform**: stand up a Neon project, `CREATE EXTENSION vector`, migrate `processes`/`stages`/`questions`/`guidance` DDL from SQLite to Postgres, rebuild the Framework Knowledge Base into `framework_kb_chunks`. Everything below depends on this. **Scope note**: the legacy SQLite `responses` table (`id`, `question_id`, `client_case_id`, `submitted_text`, `status`, `rating`, `critique`, `recommendations`, `updated_at`) was dropped, not migrated — no `responses` table exists in Postgres today. It's superseded by Phase B's `project_id`-based redesign below, so recreating the old shape now just to replace it again in Phase B would be wasted work.
- [x] **Phase A — Users & Auth**: `users` table (incl. `is_admin`), register/login, JWT issuance/verification, `get_current_user` dependency. **Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-phase-a-users-auth.md`. `require_admin` was reassigned to Phase B in that plan (it depends on the `is_admin` flag being checked in the context of project creation, which didn't exist until Phase B) — not built here, but now built as part of Phase B below. `admin_auth.py`'s stopgap shared-token gate is still untouched — Phase B's `require_admin` dependency exists now but hasn't been wired into `/api/admin/settings`; that replacement is still a future decision, not yet made. `get_current_user`/`require_admin`/`require_project_role`/`require_active_project` are not yet wired into any pre-existing endpoint (`/api/evaluate`, `/api/chat/sessions`, etc.) — those stay open/unauthenticated until Backend API Integration introduces `project_id`-scoped access control.
- [x] **Phase B — Projects**: `projects` (incl. `industry_context`, `status` starting at `Draft`) + `project_members` tables, `backend/projects_db.py`, `require_admin`/`require_project_role`/`require_active_project` dependencies, `POST /api/projects` (SystemAdmin-only), `GET /api/projects` (list), `GET /api/projects/{id}` (detail), `PATCH /api/projects/{id}`, `POST /api/projects/{id}/activate`, and the `responses` table DDL (`project_id`-based — no prior `responses` table exists to migrate from, since Phase 0 dropped the legacy one; see above). **Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-phase-b-projects.md`. **Deviated from this bullet's original wording in two ways when it landed, both deliberate at the time, both since closed**: `CASES_DATA`/`GET /api/cases`/`GET /api/case/{case_id}` were **not** removed then (would have broken the still-untouched frontend) — they were retired 2026-08-31 once Frontend GUI Overhaul landed, see that section below; and `POST /api/projects/{id}/members` was **not** built then — it was added 2026-08-31 alongside Admin UI (`POST/GET/PATCH/DELETE /api/projects/{id}/members[/{user_id}]`, see below), closing the "no way to add a ClientUser" gap. The `responses` table was DDL-only when this phase landed — Backend API Integration (below) is the first code to read/write it.
- [x] **Phase C — Engagement Knowledge Base**: `project_artifacts` table (incl. `purpose` tagging for case studies) + `project_kb_chunks` `pgvector` table (HNSW-indexed, mirroring `framework_kb_chunks`), `backend/project_artifacts_db.py`, `backend/project_knowledge_base.py` ingestion pipeline (PDF/DOCX/PPTX/TXT parsing, audio transcription with graceful degradation to a `'Transcript Needed'` status when the transcription provider isn't configured, chunking, embedding via the existing `SentenceTransformer`), and three endpoints — `POST` (upload, Consultant-only, 50MB cap), `GET` (list, any project member), `DELETE` (Consultant-only) on `/api/projects/{id}/artifacts[/{artifact_id}]`. **Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-phase-c-engagement-kb.md`. **Deviates from this bullet's original wording in two ways, both deliberate**: the merged retrieval was **not** built into `/api/evaluate` itself — Backend API Integration (below) added it as a separate `RagEngine.search_merged` method powering a new endpoint instead, since `/api/evaluate` stays untouched; and the **Engagement Documents frontend panel** was **not** built — this phase is backend-only, per its plan's explicit scope. `POST /api/projects/{id}/members` didn't exist when this phase landed (a pre-existing Phase B gap — since closed, see Phase B above) and there's still no manual-transcript-paste endpoint to complete the `'Transcript Needed'` fallback loop — that one remains a known, named gap. Original uploaded file bytes are never persisted anywhere (only the extracted/transcribed text survives, embedded into `project_kb_chunks`) — durable original-file storage was left undecided at the design level. **Audio transcription originally used AWS Transcribe/`boto3`** — added three days *after* the 2026-08-25 "GCP, not AWS" platform decision (see Production Deployment Infrastructure below) and never reconciled against it. **Migrated to Google Speech-to-Text on 2026-09-01** (`google-cloud-speech`/`google-cloud-storage`, `GCS_TRANSCRIBE_BUCKET` replacing `AWS_TRANSCRIBE_S3_BUCKET`); the codebase now has no remaining AWS dependency. **Superseded in part on 2026-09-02**: `ingest_artifact` is no longer always inline — see Async Artifact Ingestion Pipeline under Production Deployment Infrastructure below, which also adds `.md`/`.xlsx` support and (in deployed environments only) retains the original file in GCS, partially answering the "durable original-file storage" question left undecided here.

## Migration Checklist

### 1. Database Layer Overhaul — superseded by Phase A/B above
The schema goals here (drop `rating`/`critique`/`recommendations`, add `self_evaluation_notes`/`self_evaluation_status`) are delivered as part of the Users/Projects/Engagement KB spec's `responses` table redesign — see the spec linked above for the full DDL. This item is no longer tracked separately.

### 2. Backend API Integration
- [x] Connect `backend/main.py` to Neon Postgres:
  - Query **projects** dynamically — `GET /api/projects/{id}` (Phase B) already does this; this item adds `GET /api/process/{process_id}` for DB-backed stage/question retrieval (`backend/process_db.py`).
  - DB routes to get stages and questions by process ID — done via `GET /api/process/{process_id}`, nesting stages → questions → guidance.
- [x] Comparative-benchmark evaluation, delivered as a **new, additive** endpoint rather than an overhaul of the existing one (see deviation note below):
  - `RagEngine.generate_comparative_benchmarks` generates Level 1/2/3 comparative responses (a new method, not a rewrite of the existing single-rating prompt).
  - New response payload shape (`{question_id, level_1, level_2, level_3, source_chunks}`) — on the new `POST /api/projects/{project_id}/evaluate` endpoint, not on `/api/evaluate` itself.
  - `RagEngine.search_merged` merges retrieval across the Framework Knowledge Base and the current project's Engagement Knowledge Base (Phase C), source-tagged, excluding `case_study_resolution`-purpose chunks.
- [x] `POST /api/projects/{project_id}/responses` (`backend/responses_db.py`) stores submitted text, self-evaluation notes, and self-evaluation status — upsertable per `(question_id, project_id)` via `COALESCE` semantics, so a "save the answer" call followed by a separate "save the self-evaluation" call never wipes the other's data.
- [x] `GET /api/projects/{project_id}/brief` (`backend/brief.py`) outputs a compiled markdown summary brief (no HTML/PDF rendering — a deliberately simple template, per this item's own "don't over-engineer" scope note).

**Done 2026-08-28** — see `docs/superpowers/plans/2026-08-28-backend-api-integration.md`. **Deviates from this bullet's original wording in one deliberate, controller-directed way**: rather than overhauling `POST /api/evaluate` in place, every deliverable above was built as **new, additive endpoints** under `/api/projects/{project_id}/...` and `/api/process/{process_id}`. `POST /api/evaluate`, its `rating`/`critique`/`recommendations`/`source_slides` response shape, and `CASES_DATA`/`GET /api/cases`/`GET /api/case/{case_id}` are all **untouched** — the current React frontend still depends on them and this item doesn't touch the frontend. The actual cutover (pointing the frontend at the new endpoints and retiring the old ones) is deferred to Frontend GUI Overhaul below. Three real bugs were found and fixed during implementation review: an LLM response missing a benchmark level silently returned incomplete instead of falling back; the responses upsert unconditionally overwrote every column (including with `NULL`), which would have silently wiped a saved answer the first time a self-evaluation was saved separately; and `POST /api/projects/{project_id}/responses` was missing the cross-process `question_id` validation this plan's own Global Constraints required (mirrored from the evaluate endpoint).

## Beyond the POC

The BRD frames this POC as validation before a full multi-tenant build. Originally "not yet scoped" items — one has since landed, the rest remain not yet designed:
- ~~Framework Authoring Mode~~ (admin/consultant interface to define new processes, stages, and questions beyond the seeded Brand Compass configuration). **Done 2026-09-01** — see `docs/superpowers/specs/2026-09-01-framework-authoring-mode-design.md` and `docs/superpowers/plans/2026-09-01-framework-authoring-mode.md`. **Note (2026-08-26 meeting)**: whatever this authors must be treated as fixed Consultant IP going forward — the master/anchor question text itself should never be regenerated or reworded by the AI at runtime; only follow-up drill-down questions are AI-generated. See the Guided Learning Flow checklist above.
- `Owner`/`Reviewer`/`Peer` client-side role distinctions (deferred in favor of a single `ClientUser` role — see the Users/Projects/Engagement KB spec's Revision section).
- Automatic mapping of a `questions.owner_role` string (e.g. "CMO") to a specific project member — for now, any `ClientUser` can answer any question.
- SSO / enterprise identity (Azure AD, Cognito, etc.) — the near-term auth design (Phase A above) is deliberately simple, built-in email/password.
- Multi-**firm** isolation (multiple consulting firms sharing one deployment). Note this is narrower than it used to be: per-*project* isolation (one customer engagement's data kept separate from another's) is now addressed by the Foundational Work above, once built, via `pgvector` row-level `project_id` scoping — what remains open is isolating separate consulting *firms* from each other on a shared instance.
- **Four additional product modules** beyond Insights/Capability Building — management process building, organization transparency building, performance & potential evaluation, and DIY consulting — sharing the same underlying corpus but with dramatically different user experiences per the Aug 24 meeting. A follow-up stakeholder call is scheduled to go deeper into these; see `documentation/product/functional-spec.md` §5 for the framing captured so far.
- Neon Object Storage / Functions / AI Gateway — explicitly out of scope per the Neon spec; original uploaded file storage (as opposed to their vector embeddings) is still an open question, not decided.
